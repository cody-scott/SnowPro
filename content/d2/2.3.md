## What you pay for

| Category | Includes |
|---|---|
| **Compute** | **Virtual warehouses** (per second, 60 s minimum); **serverless features** (Snowpipe, automatic clustering, materialized view maintenance, search optimization, serverless tasks, query acceleration, replication, DMFs…), billed by Snowflake-managed compute; **Cloud Services** above the 10% daily adjustment; AI services billed by tokens or credits. |
| **Storage** | Average compressed TB per month: tables (active data **plus Time Travel and Fail-safe**), stages, and the changed data in clones. |
| **Data transfer** | **Egress** to another region or cloud (unloading, replication, external functions). **Ingress is free**, and so is transfer within the same region. |

- Credit cost depends on **edition, cloud and region**. Customers pay with **on-demand** credits or **capacity** (pre-purchased) contracts.
- A large Fail-safe or Time Travel footprint is a common cause of unexpected storage cost. Check `TABLE_STORAGE_METRICS` (active / time travel / failsafe bytes), and use **transient** tables for data you can recreate.

## Resource monitors (warehouses only)

- Set a **credit quota** over an interval (`FREQUENCY` = `DAILY`, `WEEKLY`, `MONTHLY`, `YEARLY`, `NEVER`). By default a monitor starts right away and resets at the start of each calendar month. Resets always happen at **12:00 AM UTC**.
- The quota counts warehouse credits **plus the cloud services credits used to support them**, and **ignores the 10% cloud services adjustment**. Credits that are never billed still count toward the limit.
- **Triggers** fire at a percentage of the quota (values above 100% are allowed). Each monitor can have **one Suspend, one Suspend Immediate and up to five Notify** actions.
- Trigger actions:

| Action | Effect |
|---|---|
| `NOTIFY` | Alert only |
| `SUSPEND` | Notify, then suspend the warehouses **after running statements finish** |
| `SUSPEND_IMMEDIATE` | Notify, then suspend and **cancel running statements** |

- Scope: an account can have **one account monitor** (all warehouses) and many **warehouse monitors**. A warehouse monitor can cover many warehouses, but **each warehouse can be assigned to only one monitor**.
- **Only ACCOUNTADMIN can create** resource monitors. It can grant other roles privileges to view and modify them.
- Notifications go to account administrators who have notifications enabled. Non-admin users can get email notifications too, but only for warehouse monitors.
- They only track **warehouse** credits. They **can't** limit serverless features or AI services; use budgets for those.

```sql
CREATE RESOURCE MONITOR rm_etl WITH CREDIT_QUOTA = 500 FREQUENCY = MONTHLY START_TIMESTAMP = IMMEDIATELY
  TRIGGERS ON 80 PERCENT DO NOTIFY ON 100 PERCENT DO SUSPEND ON 110 PERCENT DO SUSPEND_IMMEDIATE;
ALTER WAREHOUSE etl_wh SET RESOURCE_MONITOR = rm_etl;
```

## Budgets

- A budget sets a **monthly spending limit** (in credits, from 12:00 AM UTC on the 1st) for the **whole account** (the account budget, which you activate) or a **custom budget** for a group of objects added individually or by **tag**. It covers warehouses **and serverless features**.
- The limit is for **alerting only**. It **notifies** (email, a cloud queue such as SNS / Event Grid / Pub/Sub, or a webhook such as Slack or Teams) when spend is **projected** to exceed the limit. It can also call **stored procedures** at thresholds, which could, for example, suspend warehouses. It never suspends anything on its own.

> **Exam tip:** "Hard stop on a warehouse's credits" → **resource monitor**. "Track spend across serverless features / a project's objects" → **budget**.

## Where to look: ACCOUNT_USAGE vs INFORMATION_SCHEMA

| | `SNOWFLAKE.ACCOUNT_USAGE` | `<db>.INFORMATION_SCHEMA` |
|---|---|---|
| Scope | Whole account | One database (plus account-level table functions) |
| Latency | **45 min to 3 h** | **None** (real time) |
| Retention | **1 year** | **7 days to 6 months**, depending on the view or function |
| Dropped objects | **Included** | Not included |

`ORGANIZATION_USAGE` covers **all accounts** in the organization (for example, `USAGE_IN_CURRENCY_DAILY`). Every user can see the `SNOWFLAKE` database, but only **ACCOUNTADMIN** can open its schemas by default. ACCOUNTADMIN can give other roles access with `GRANT IMPORTED PRIVILEGES ON DATABASE SNOWFLAKE`, or more narrowly by granting a **SNOWFLAKE database role** (such as `USAGE_VIEWER` or `GOVERNANCE_VIEWER`).

**Views to know**

| View | Shows |
|---|---|
| `WAREHOUSE_METERING_HISTORY` | Credits per warehouse per hour |
| `METERING_DAILY_HISTORY` | Daily credits by service type, including the **cloud services adjustment** (what's actually billed) |
| `METERING_HISTORY` | Hourly credits for warehouses **and serverless** services |
| `QUERY_HISTORY` | Every query: user, role, warehouse, elapsed and queued time, bytes scanned/spilled |
| `QUERY_ATTRIBUTION_HISTORY` | **Compute cost per query** (excludes warehouse idle time) |
| `WAREHOUSE_LOAD_HISTORY` | Running vs **queued** load (helps size warehouses and multi-cluster settings) |
| `STORAGE_USAGE`, `DATABASE_STORAGE_USAGE_HISTORY`, `TABLE_STORAGE_METRICS` | Storage over time and by table |
| `LOGIN_HISTORY` | Sign-ins, including failures |

## Attribute and control cost

- **Object tags** on warehouses, databases and users let you group spend by team or project (join tag references with metering views).
- **`QUERY_TAG`** (session, user or account parameter) labels queries, so you can attribute a shared warehouse's cost.
- Use separate **warehouses per workload** to get clean attribution.
- Warehouse guardrails: **`STATEMENT_TIMEOUT_IN_SECONDS`** (default 172,800 s = 2 days) cancels runaway queries; `STATEMENT_QUEUED_TIMEOUT_IN_SECONDS` cancels queries that wait in the queue too long; plus **auto-suspend**.

## Monitoring tools

- **Snowsight → Admin → Cost Management:** spend overview, consumption by service and warehouse, budgets and resource monitors, plus **cost insights** (recommendations such as unused warehouses or rarely used tables).
- **Snowsight → Monitoring:** **Query History** (the last **14 days**; user details only for the last 7; the Query Profile per query), Copy History, Task History.
- **Alerts:** `CREATE ALERT` checks a SQL condition on a schedule and runs an action, for example `SYSTEM$SEND_EMAIL` through a **notification integration**.
- **Logging, tracing and metrics** (Snowflake's observability features): log messages and trace events from UDFs, procedures and apps, plus CPU and memory metrics, are collected into an **event table**.

> **Exam tip:** "Most recent few minutes" → INFORMATION_SCHEMA. "Last 6 months, including dropped tables" → ACCOUNT_USAGE. "Across all accounts" → ORGANIZATION_USAGE.
