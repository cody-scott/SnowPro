## Access control frameworks

Snowflake combines two models:

| Model | Meaning |
|---|---|
| **RBAC** (role-based) | Privileges are granted to **roles**; roles are granted to **users** (or to other roles). Users never hold privileges directly. |
| **DAC** (discretionary) | Every securable object has exactly **one owner role** (the role with `OWNERSHIP`), and the owner can grant access to it. |

Key terms: **securable object** (thing you can grant on) → **privilege** (`SELECT`, `USAGE`, `CREATE TABLE`, `OWNERSHIP`…) → **role** → **user**.

- To query a table a role needs `USAGE` on the **database** and **schema** *and* `SELECT` on the table. (Plus `USAGE` on a warehouse to run it.)
- Privileges granted to a role are **inherited** by every role above it in the hierarchy.
- `GRANT OWNERSHIP ON … TO ROLE x COPY CURRENT GRANTS` transfers ownership but keeps the existing grants (`REVOKE CURRENT GRANTS` drops them).

## System-defined roles

```
            ACCOUNTADMIN
           /            \
   SECURITYADMIN       SYSADMIN
         |                 |
     USERADMIN       (custom roles)
          \               /
               PUBLIC
```

| Role | Purpose |
|---|---|
| **ORGADMIN** | Organization-level: create accounts, view usage across accounts. (**GLOBALORGADMIN** in the organization account.) Not part of the account hierarchy. |
| **ACCOUNTADMIN** | Top-level role; holds SYSADMIN + SECURITYADMIN. Billing, resource monitors, account parameters. |
| **SECURITYADMIN** | `MANAGE GRANTS` — can grant/revoke any privilege on any object. Manages network policies. Inherits USERADMIN. |
| **USERADMIN** | `CREATE USER` and `CREATE ROLE`. |
| **SYSADMIN** | Creates warehouses, databases and other objects. |
| **PUBLIC** | Automatically granted to every user and role. |

**Best practices**

- Grant every custom role (or the top of a custom role tree) **to SYSADMIN**, so admins can manage the objects those roles own.
- Grant ACCOUNTADMIN to a **small number of users (at least two)**, require **MFA**, and don't make it anyone's default role or use it to create objects.

## Database roles, secondary roles, future grants

- **Database roles** live inside a database and can only hold privileges on objects in it. They can't be a session's primary role; you grant them to account roles (or to a **share**, the usual reason to use them).
- **Primary vs secondary roles:** `USE SECONDARY ROLES ALL` adds the privileges of all your other granted roles to the session. **Creating** objects uses only the **primary** role, which becomes the owner.
- **Future grants:** `GRANT SELECT ON FUTURE TABLES IN SCHEMA s TO ROLE r` applies to objects created later.
- **Managed access schema** (`CREATE SCHEMA … WITH MANAGED ACCESS`): object owners can no longer grant on their own objects; only the **schema owner** or a role with `MANAGE GRANTS` can grant. This centralizes grant decisions.

## Authentication

| Method | Use for |
|---|---|
| **MFA** | Human users who sign in with a password. Duo push, authenticator apps (TOTP) and passkeys. Snowflake is phasing out single-factor password sign-in. |
| **Federated auth / SSO** | **SAML 2.0** identity provider (Okta, Microsoft Entra ID, ADFS…). The IdP authenticates; Snowflake trusts it. |
| **Key-pair auth** | Service users, drivers and connectors. RSA key pair (2048-bit minimum). A user can hold **two public keys** (`RSA_PUBLIC_KEY`, `RSA_PUBLIC_KEY_2`) so keys can be rotated without downtime. |
| **OAuth** | **Snowflake OAuth** (Snowflake issues tokens to clients such as Tableau) or **External OAuth** (Okta, Entra ID… issues the tokens). |
| **Programmatic access tokens (PATs)** | Token-based access for scripts and tools, used in place of a password. |
| **Workload identity federation** | Service workloads authenticate with their cloud identity (AWS IAM, Azure, GCP) and need no stored secret. |

- **User `TYPE`:** `PERSON` (humans), `SERVICE` (no password or MFA allowed; use key-pair, OAuth or PAT), `LEGACY_SERVICE` (transitional).
- **SCIM** lets an IdP automatically create, update and disable users and roles.
- **Policies** applied to the account or individual users: **authentication policies** (allowed methods, clients, MFA enrollment), **password policies** (length, complexity, age, lockout), **session policies** (idle timeout, 4 hours by default).

## Network security

- **Network policies** allow or block client IP addresses. Their lists come from **network rules** (IPv4 ranges, or private endpoint IDs such as AWS VPC endpoint IDs). A blocked entry wins over an allowed one.
- They can be applied to the **account**, a **user** or a **security integration**. **The most specific one wins:** a user-level policy overrides the account-level one. Only one policy can be active at each level.
- Creating policies requires SECURITYADMIN or higher (or `CREATE NETWORK POLICY`).
- **Private connectivity** (AWS PrivateLink, Azure Private Link, GCP Private Service Connect) keeps traffic off the public internet. Requires **Business Critical**.

## Encryption

- All data is **encrypted at rest (AES-256) and in transit (TLS 1.2+)**, on every edition and with no configuration.
- **Hierarchical key model:** root key → account master keys → table master keys → file keys. Each key encrypts the keys below it, which limits how much data any one key covers.
- **Key rotation:** Snowflake-managed keys are rotated automatically **every 30 days**. Retired keys can still decrypt older data but are no longer used to encrypt new data.
- **Periodic rekeying (Enterprise+):** data encrypted with a key **older than 1 year** is re-encrypted with a new key, in the background.
- **Tri-Secret Secure (Business Critical+):** a customer-managed key in the cloud provider's KMS is combined with a Snowflake-managed key to form a composite master key. If the customer **revokes** its key, Snowflake can no longer decrypt the data.

## Trust Center

Snowsight's **Trust Center** scans the account against security best practices (scanner packages such as Security Essentials and the **CIS Benchmarks**), lists findings with suggested fixes, and can notify you when something new turns up.

> **Exam tip:** "Who can create users/roles?" → USERADMIN. "Who can grant anything on anything?" → SECURITYADMIN (`MANAGE GRANTS`). "Who should own custom roles?" → granted to SYSADMIN. "User policy vs account policy?" → the user policy wins.
