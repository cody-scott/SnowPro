## Access control frameworks

Snowflake combines three models:

| Model | Meaning |
|---|---|
| **RBAC** (role-based) | Privileges are granted to **roles**; roles are granted to **users** (or to other roles). This is the usual way to manage access. |
| **DAC** (discretionary) | Every securable object has exactly **one owner role** (the role with `OWNERSHIP`), and the owner can grant access to it. |
| **UBAC** (user-based) | Privileges granted **directly to a user**. They count only when the session runs `USE SECONDARY ROLES ALL`. |

Key terms: **securable object** (thing you can grant on) → **privilege** (`SELECT`, `USAGE`, `CREATE TABLE`, `OWNERSHIP`…) → **role** → **user**.

- To query a table a role needs `USAGE` on the **database** and **schema** *and* `SELECT` on the table. (Plus `USAGE` on a warehouse to run it.)
- Privileges granted to a role are **inherited** by every role above it in the hierarchy.
- `GRANT OWNERSHIP ON … TO ROLE x COPY CURRENT GRANTS` transfers ownership but keeps the existing grants (`REVOKE CURRENT GRANTS` drops them).

## System-defined roles

```
            ACCOUNTADMIN
           /            \
   SECURITYADMIN       SYSADMIN
         |                 |
     USERADMIN       (custom roles)
          \               /
               PUBLIC
```

| Role | Purpose |
|---|---|
| **GLOBALORGADMIN** / **ORGADMIN** | Organization-level: create accounts, view usage across accounts. GLOBALORGADMIN exists only in the **organization account**; ORGADMIN (in a regular account) is being phased out in its favor. Neither is part of the account hierarchy. |
| **ACCOUNTADMIN** | Top-level role; holds SYSADMIN + SECURITYADMIN. Billing, resource monitors, account parameters. |
| **SECURITYADMIN** | `MANAGE GRANTS` — can grant/revoke any privilege on any object. Manages network policies. Inherits USERADMIN. |
| **USERADMIN** | `CREATE USER` and `CREATE ROLE`. |
| **SYSADMIN** | Creates warehouses, databases and other objects. |
| **PUBLIC** | Automatically granted to every user and role. |

**Best practices**

- Grant every custom role (or the top of a custom role tree) **to SYSADMIN**, so admins can manage the objects those roles own.
- Grant ACCOUNTADMIN to a **small number of users (at least two)**, require **MFA**, and don't make it anyone's default role or use it to create objects.

## Database roles, secondary roles, future grants

- **Database roles** live inside a database and can only hold privileges on objects in it. They can't be activated in a session at all, as either the primary or a secondary role. Grant them to account roles, or to a **share** (`GRANT DATABASE ROLE … TO SHARE`) to share privileges on one database.
- **Primary vs secondary roles:** `USE SECONDARY ROLES ALL` adds the privileges of all your other granted roles to the session. **Creating** objects uses only the **primary** role, which becomes the owner.
- **Future grants:** `GRANT SELECT ON FUTURE TABLES IN SCHEMA s TO ROLE r` applies to objects created later. If both the database and the schema have future grants for the same object type, the **schema-level grants win** and the database-level ones are ignored.
- **Managed access schema** (`CREATE SCHEMA … WITH MANAGED ACCESS`): object owners can no longer grant on their own objects; only the **schema owner** or a role with `MANAGE GRANTS` can grant. This centralizes grant decisions.

## Authentication

| Method | Use for |
|---|---|
| **MFA** | Human users who sign in with a password. Second factor: **passkey** (recommended), **authenticator app** (TOTP) or **Duo**. |
| **Federated auth / SSO** | **SAML 2.0** (native support for Okta and Microsoft Entra ID; most other SAML 2.0 IdPs also work) or OpenID Connect. The IdP authenticates; Snowflake trusts it. |
| **Key-pair auth** | Service users, drivers and connectors. RSA key pair (**2048-bit minimum**). Rotate with `ALTER USER … ROTATE KEY PAIR` (recommended: the old key keeps working for a grace period), or by swapping between the two key slots `RSA_PUBLIC_KEY` and `RSA_PUBLIC_KEY_2`. |
| **OAuth** | **Snowflake OAuth** (Snowflake issues tokens to clients such as Tableau) or **External OAuth** (Okta, Entra ID… issues the tokens). |
| **Programmatic access tokens (PATs)** | Token-based access for scripts and tools, used in place of a password. By default the user must be subject to a **network policy** to authenticate with one. |
| **Workload identity federation** | Service workloads authenticate with their cloud platform's own identity (AWS IAM roles, Microsoft Entra ID, Google Cloud service accounts) and need no stored secret. |

**Single-factor passwords are being retired** (rolling out by account):

| Phase | When | Effect |
|---|---|---|
| 1 | Sep 2025 – Jan 2026 | MFA required for password sign-ins to **Snowsight** |
| 2 | May – Jul 2026 | **New** human users need a second factor everywhere; new users can't be `LEGACY_SERVICE` |
| 3 | Aug – Oct 2026 | **No** user can sign in with a password alone; `LEGACY_SERVICE` users are converted to `SERVICE` |

- **User `TYPE`:** `PERSON` (humans, the default), `SERVICE` (can't use a password or enroll in MFA; uses key-pair, OAuth, PATs or workload identity), `SERVICE_AGENT` (AI agents; non-interactive like SERVICE), `LEGACY_SERVICE` (deprecated).
- **SCIM 2.0** lets an IdP (Okta, Microsoft Entra ID or a custom one) automatically create, update and disable users and roles.
- **Policies** applied to the account or individual users: **authentication policies** (allowed methods, clients, MFA enrollment), **password policies** (length, complexity, age, lockout), **session policies** (idle timeout: by default **4 hours** for programmatic sessions and **18 hours** in Snowsight; configurable from 5 minutes to 24 hours).

## Network security

- **Network policies** allow or block incoming requests. Their allowed and blocked lists hold **network rules**, which group identifiers: IPv4/IPv6 ranges, or private endpoint IDs (`AWSVPCEID`, `AZURELINKID`). Adding anything to the allowed list blocks everything else of that type, and an identifier in both lists is **blocked**.
- They can be applied to the **account**, a **user** or a **security integration**. **The most specific one wins:** security integration > user > account. Only one network policy can be active on the account at a time.
- Creating one requires SECURITYADMIN or higher, or the global `CREATE NETWORK POLICY` privilege. Activating one requires SECURITYADMIN or higher, or `ATTACH POLICY`.
- **Private connectivity** (AWS PrivateLink, Azure Private Link, GCP Private Service Connect) keeps traffic off the public internet. Requires **Business Critical**.

## Encryption

- All customer data is **encrypted by default**, at rest (strong AES encryption) and in transit (TLS), on every edition and with no configuration.
- **Hierarchical key model:** root key → account master keys → table master keys → file keys. Each key encrypts the keys below it, which limits how much data any one key covers.
- **Key rotation:** Snowflake-managed keys are rotated automatically once they're **more than 30 days old**. Retired keys can still decrypt older data but are no longer used to encrypt new data.
- **Periodic rekeying (Enterprise+):** data encrypted with a key **older than 1 year** is re-encrypted with a new key, in the background.
- **Tri-Secret Secure (Business Critical+):** a customer-managed key in the cloud provider's KMS is combined with a Snowflake-managed key to form a composite master key. If the customer **revokes** its key, Snowflake can no longer decrypt the data.

## Trust Center

Snowsight's **Trust Center** groups **scanners** into **scanner packages** (for example **Security Essentials**, **CIS Benchmarks** and **AI Security**). Schedule-based scanners check settings on a schedule, and event-driven scanners flag events such as sign-ins from unusual IP addresses. It lists violations with how to fix them and can send notifications.

> **Exam tip:** "Who can create users/roles?" → USERADMIN. "Who can grant anything on anything?" → SECURITYADMIN (`MANAGE GRANTS`). "Who should own custom roles?" → granted to SYSADMIN. "User policy vs account policy?" → the user policy wins (a security integration policy beats both).
