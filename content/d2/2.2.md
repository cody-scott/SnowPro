## Snowflake Horizon

**Horizon Catalog** is Snowflake's name for its built-in governance features: access control, data protection policies, classification, lineage, data quality and discovery. Most of the policy features below require **Enterprise edition or higher**.

## Secure views and secure UDFs

- A **secure view** (`CREATE SECURE VIEW`) hides its definition from everyone except the owner role (`GET_DDL` and `SHOW VIEWS` show the text only to the owner). It also turns off optimizations that could expose filtered-out rows indirectly.
- The trade-off: secure views can be **slower**. Use them when the data must be protected (sharing, row-level filtering), not by default.
- **Secure UDFs** and **secure materialized views** work the same way. Secure objects are the standard way to expose views and functions through **Secure Data Sharing**.
- Check `IS_SECURE` in `SHOW VIEWS` or `INFORMATION_SCHEMA.VIEWS`.

## Column-level security: masking policies

- A **masking policy** is a schema-level object holding a SQL expression that rewrites a column's value **at query time**, based on context such as `CURRENT_ROLE()` or `IS_ROLE_IN_SESSION()`. The data stored in the table never changes.
- Write it once and apply it to many columns: `ALTER TABLE t MODIFY COLUMN email SET MASKING POLICY pii_mask`.
- The policy's **input and output data types must match** the column type. A column can have **only one** masking policy.
- **Conditional masking:** the policy signature can take extra columns (for example, unmask only when `consent = TRUE`).
- **External tokenization:** data is tokenized before it's loaded; the masking policy calls an **external function** to detokenize it for authorized roles.
- Policies apply to **everyone**, including the table owner and ACCOUNTADMIN, unless the policy body exempts them.

```sql
CREATE MASKING POLICY pii_mask AS (val STRING) RETURNS STRING ->
  CASE WHEN IS_ROLE_IN_SESSION('PII_READER') THEN val ELSE '***MASKED***' END;
```

## Row-level security: row access policies

- A **row access policy** returns a **BOOLEAN** for each row. Rows that return FALSE are left out of the result. Policies often look up a **mapping table** (for example, role → allowed region).
- A table or view can have **only one** row access policy at a time.
- When a table has both, the **row access policy is evaluated before masking policies**.

## Privacy policies

| Policy | Effect |
|---|---|
| **Aggregation policy** | Queries must **aggregate** rows into groups of at least `MIN_GROUP_SIZE`; individual rows can't be returned. |
| **Projection policy** | A column **can't appear in the SELECT output**, but can still be used in `WHERE`, `JOIN` and `GROUP BY`. |
| **Differential privacy** (privacy policies) | Adds statistical noise to results and limits how much can be learned about any individual (privacy budget). |

## Object tagging

- A **tag** is a schema-level object; you set a **string value** for it on an object (`ALTER TABLE t SET TAG cost_center = 'finance'`). `ALLOWED_VALUES` limits the values that can be used.
- An object can have up to **50 tags**.
- **Tag lineage:** a tag set on a parent object is **inherited** by child objects (database → schema → table → column) unless the child overrides it.
- **Tag-based masking:** attach masking policies to a **tag**, and every column carrying that tag is masked automatically (one policy per data type per tag). This is how masking scales to many tables.
- Find tags with `TAG_REFERENCES` (Information Schema table function) and `ACCOUNT_USAGE.TAG_REFERENCES`. Tags are also used for **cost attribution** (see 2.3).

## Sensitive data classification

- Snowflake inspects column values and assigns **semantic categories** (`NAME`, `EMAIL`, `PHONE_NUMBER`, `NATIONAL_IDENTIFIER`…) and **privacy categories** (`IDENTIFIER`, `QUASI_IDENTIFIER`, `SENSITIVE`).
- Run it manually with `SYSTEM$CLASSIFY`, or automatically with a **classification profile** set on a database or schema.
- Results are stored as **system tags** (`SNOWFLAKE.CORE.SEMANTIC_CATEGORY`, `SNOWFLAKE.CORE.PRIVACY_CATEGORY`). You can pair them with tag-based masking.

## Access history and lineage

- `SNOWFLAKE.ACCOUNT_USAGE.ACCESS_HISTORY` (Enterprise) records, for each query, **which objects and columns were read and written** (`DIRECT_OBJECTS_ACCESSED`, `BASE_OBJECTS_ACCESSED`, `OBJECTS_MODIFIED`). Use it for audits and to find unused data.
- **Base objects** are the underlying tables behind the views a query used.
- **Lineage** in Snowsight shows how data flows from upstream to downstream tables and columns. `OBJECT_DEPENDENCIES` lists which objects reference others (for example, views on tables).

## Data quality: data metric functions (DMFs)

- **System DMFs** in `SNOWFLAKE.CORE`: `NULL_COUNT`, `DUPLICATE_COUNT`, `UNIQUE_COUNT`, `ROW_COUNT`, `FRESHNESS`, and others. You can also write **custom DMFs**.
- Attach them to a table or view and set a schedule with the table's **`DATA_METRIC_SCHEDULE`**, which applies to every DMF on that table (for example, `'60 MINUTE'`, a cron expression or `'TRIGGER_ON_CHANGES'`).
- Results are written to `SNOWFLAKE.LOCAL.DATA_QUALITY_MONITORING_RESULTS`. DMFs run on **serverless** compute.

> **Exam tip:** "Hide the column value" → masking policy. "Hide rows" → row access policy. "Hide the view's SQL" → secure view. "Mask every column labelled PII at once" → tag-based masking. "Who read this column last month?" → ACCESS_HISTORY.
