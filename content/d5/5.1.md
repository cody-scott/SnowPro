## Data protection at a glance

| Feature | Protects against | Who uses it | How long |
|---|---|---|---|
| **Time Travel** | Mistakes: bad updates, deletes, drops | **You** (`AT` / `BEFORE`, `UNDROP`, clone) | 0–1 day (Standard); up to **90 days** for permanent objects (Enterprise+) |
| **Fail-safe** | Disaster after Time Travel ends | **Only Snowflake Support** (best effort) | **7 days** for permanent tables; **none** for transient and temporary |
| **Cloning** | Need a copy for dev / test / backup | You | Instant, zero-copy |
| **Replication & failover** | Region or cloud outage; migration; sharing across regions | You (target account) | Continuous refreshes |

Lifecycle of a changed row: **current data → Time Travel (retention period) → Fail-safe (7 days) → gone.** Both Time Travel and Fail-safe data count toward **storage cost**.

## Time Travel

- Query, clone or restore data **as it was** at a point in the past:

```sql
SELECT * FROM orders AT (OFFSET => -60*30);                    -- 30 minutes ago
SELECT * FROM orders AT (TIMESTAMP => '2026-11-20 09:00'::TIMESTAMP_LTZ);
SELECT * FROM orders BEFORE (STATEMENT => '01b2...');          -- just before a query ran
CREATE TABLE orders_fix CLONE orders BEFORE (STATEMENT => '01b2...');
UNDROP TABLE orders;   -- also UNDROP SCHEMA / DATABASE
```

- Retention is set with **`DATA_RETENTION_TIME_IN_DAYS`** (account, database, schema or table). Default **1 day**. **0 turns Time Travel off** for that object.

| Edition | Permanent objects | Transient / temporary |
|---|---|---|
| Standard | 0 or 1 day | 0 or 1 day |
| **Enterprise+** | **0–90 days** | 0 or 1 day |

- **`MIN_DATA_RETENTION_TIME_IN_DAYS`** (account level, ACCOUNTADMIN) sets a floor: effective retention = MAX(the two parameters).
- **`UNDROP`** restores the most recent dropped version. If an object with the same name now exists, rename it first. Changing the retention of a **dropped** object has no effect until you undrop it.
- Increasing retention keeps data that's still in Time Travel longer; decreasing it moves older data into Fail-safe.
- Querying further back than the retention period returns an **error**.

## Fail-safe

- A **non-configurable 7-day** period that starts **after Time Travel ends**, for permanent tables only.
- **Not for you to query.** Only **Snowflake Support** can recover data, on a **best-effort** basis, which can take hours to days. Recovery uses serverless compute.
- **Transient** and **temporary** tables have **no Fail-safe** (and at most 1 day of Time Travel), which is why they cost less to store.
- Snowflake suggests **Backups** (point-in-time snapshots that you control) for critical data instead of relying on Fail-safe.

## Cloning (zero-copy)

- `CREATE { DATABASE | SCHEMA | TABLE | ... } new CLONE source [AT | BEFORE (...)]` makes a **metadata-only copy**: no data is copied, so it's **instant** and uses **no extra storage** at first. Storage is used only for data that's **changed** in either object afterwards.
- The clone is **writable and independent**: changes to one don't affect the other.
- You can clone **databases, schemas, tables**, plus streams, tasks, external stages, file formats, sequences and more. Combine with Time Travel to clone a past state.
- **What carries over:**
  - Cloning a **database or schema** copies the **grants on its child objects**, but not the grants on the container itself. Cloning a **table** copies no grants unless you add **`COPY GRANTS`**.
  - **Tasks** in a cloned database/schema are **suspended**. Cloned tables have **Automatic Clustering suspended**.
  - **Internal named stages** are cloned only with `INCLUDE INTERNAL STAGES`; table stages come over **empty**. Pipes that reference internal stages aren't cloned; pipes on external stages are.
  - A cloned table has **no load history**, so COPY may reload files the source already loaded.
  - Unconsumed records in **streams** inside a cloned database/schema are inaccessible.
- Permanent ↔ transient clones aren't allowed for tables (both must be the same type).

## Replication and failover

- Replicates objects from a **source account** to **target accounts in the same organization**, **across regions and clouds**. The target copies are **secondary** objects and are **read-only**.
- **Replication group:** a set of objects replicated together, with **point-in-time consistency**. **Failover group:** a replication group whose secondary can be **promoted to primary** (read-write) during an outage.

| Feature | Edition |
|---|---|
| **Database and share replication** (replication groups) | **All editions** |
| Account objects (users, roles, warehouses, network policies, integrations, parameters, resource monitors…) | **Business Critical+** |
| **Failover groups** (failover / failback) | **Business Critical+** |
| **Client Redirect** (connection objects) | **Business Critical+** |

- Setup: an organization admin **enables replication** for the accounts → `CREATE FAILOVER GROUP ... OBJECT_TYPES = DATABASES, ROLES, ... ALLOWED_ACCOUNTS = org.acct2` in the source → create the secondary group in the target `AS REPLICA OF` → refresh on a **`REPLICATION_SCHEDULE`** (recommended) or manually.
- **Failover:** `ALTER FAILOVER GROUP fg PRIMARY` in the target account makes it the primary.
- **Client Redirect:** a **connection object** gives a URL (`org-connection.snowflakecomputing.com`) that points at the account with the primary connection. After failover you promote the connection in the other account and **clients keep the same URL**.
- **Cost:** billed to the **target** account: **data transfer** between regions plus **compute** for refreshes, plus storage of the replicas.
- Inbound shares (imported databases) **can't be replicated**.

> **Exam tip:** "Recover a table dropped yesterday" → **UNDROP** (Time Travel). "Recover data from 10 days ago on a 1-day table" → only **Snowflake Support via Fail-safe**, if within 7 days. "Keep working through a region outage with the same connection URL" → **failover group + Client Redirect (Business Critical)**.
