## How Secure Data Sharing works

- A **provider** shares selected database objects with **consumer** accounts. **No data is copied or moved**: consumers query the provider's data in place through Snowflake's services layer and metadata.
- **Consumers pay only for compute** (their warehouses) to query shared data. **Providers pay for storage**. Shared data uses **no storage in the consumer account**.
- Shared objects are **read-only** to consumers. Changes the provider makes (new rows, new objects added to the share) are visible **immediately**. The provider can **revoke** access at any time.
- Any full Snowflake account can be both a provider and a consumer.

**Shareable objects:** databases, schemas, **tables**, dynamic tables, external tables, Iceberg tables, **secure views** and **secure materialized views**, regular views (see below), secure and non-secure UDFs (depending on language), Cortex Search services, semantic views and some models.

## Shares and direct shares

A **share** is a named object holding the grants for what's shared and the list of consumer accounts. A **direct share** is a share sent straight to specific accounts.

```sql
-- Provider (ACCOUNTADMIN or a role with the global CREATE SHARE privilege)
CREATE SHARE sales_s;
GRANT USAGE  ON DATABASE sales        TO SHARE sales_s;
GRANT USAGE  ON SCHEMA   sales.public TO SHARE sales_s;
GRANT SELECT ON TABLE    sales.public.orders TO SHARE sales_s;
ALTER SHARE sales_s ADD ACCOUNTS = myorg.partner_acct;

-- Consumer
CREATE DATABASE snow_sales FROM SHARE provider_acct.sales_s;
GRANT IMPORTED PRIVILEGES ON DATABASE snow_sales TO ROLE analyst;
```

- Grant privileges to a share **directly** or through a **database role** (the consumer then grants that database role to its own roles, for finer access control).
- **Direct shares work only between accounts in the same region.** To share **across regions or clouds**, use a **listing with Cross-Cloud Auto-Fulfillment** (or replicate the database yourself).
- **Views:** by default a share accepts **only secure objects** (secure views, secure UDFs). Snowflake recommends secure views; to share regular views, create the share with **`SECURE_OBJECTS_ONLY = FALSE`**.
- **Data from several databases:** share a secure view that references them and grant **`REFERENCE_USAGE`** on each referenced database to the share. (This can't be done with database roles.)
- Consumers can create **streams** on shared tables or secure views if the provider enables **change tracking** and enough retention.
- A secure view joined to a **mapping table** on **`CURRENT_ACCOUNT()`** lets one share show different rows to different consumer accounts.

## Consumers and imported databases

- A consumer creates **one database per share** (`CREATE DATABASE ... FROM SHARE`), then grants **`IMPORTED PRIVILEGES`** on it to roles (or, if the provider used database roles, grants those **database roles** to its account roles). Creating it needs the global **`CREATE DATABASE`** and **`IMPORT SHARE`** privileges (ACCOUNTADMIN has them).
- Imported databases are **read-only**. Consumers **can't**: modify data or create objects in them, **clone** them, use **Time Travel** on them, or **replicate** them.
- In Snowsight: **Data sharing → Internal sharing → Shared With You** (listings and direct shares available to your account).

## Resharing

- A consumer can **reshare** data from a direct share **only if the provider allowed it**, and **only with accounts in the consumer's own organization** (check `resharing_settings` in `SHOW DATABASES`).
- To reshare, the consumer creates a **secure view** in its own database over the imported data, then shares that view. Tables, dynamic tables and views can be reshared; UDFs can't. Downstream consumers see only what the resharer can see.

## Reader accounts

- For consumers **without a Snowflake account**. The provider creates one with **`CREATE MANAGED ACCOUNT`** (ACCOUNTADMIN by default).
- The reader account is **owned and paid for by the provider**, including its warehouse credits. Use **resource monitors** to cap them.
- A reader account can consume data **only from the provider that created it**.
- It's **query-only**: no loading data (`COPY INTO <table>`, `CREATE PIPE`), no `INSERT` / `UPDATE` / `DELETE` / `MERGE`, no masking or row access policies. It can create things like materialized views over the shared data.
- Default limit: **75** reader accounts per provider.

## Data clean rooms

- **Snowflake Data Clean Rooms** let several parties **analyze combined data without exposing the raw rows** to each other. Each party controls which **templates** (approved queries) can run on its data and which columns and policies apply.
- Roles in a collaboration: **owner** (creates it and invites collaborators), **data provider** (offers data), **analysis runner** (runs permitted templates).
- Typical use: advertisers and publishers measuring audience overlap without sharing customer lists.
- **Data providers need Enterprise Edition**; owners and analysis runners can use Standard. Not available on trial accounts.

## Ways to share: summary

| Option | Use when |
|---|---|
| **Direct share** | Specific accounts in **your region**; simple, no extra metadata |
| **Listing** (private or Marketplace) | Across regions/clouds, metadata and sample queries, usage metrics, paid access, Native Apps (see 5.3) |
| **Data Exchange** | A private group of accounts you invite and manage |
| **Reader account** | The consumer has no Snowflake account |
| **Data clean room** | Joint analysis where raw data must stay hidden |

> **Exam tip:** "Who pays for the consumer's queries?" → the **consumer** (their warehouse), except with a **reader account**, where the **provider** pays. "Share with an account in another region" → **listing with auto-fulfillment** (or replication), not a direct share.
