## Snowpipe (continuous file loading)

- A **pipe** is a schema object that holds **one `COPY INTO` statement**. Snowpipe runs it on **serverless compute** for each new file, typically **within a minute** of learning about it. You can't edit a pipe's definition; you recreate it (which drops its load metadata).
- Snowpipe **learns about new files** in two ways:

| Mode | How | Where |
|---|---|---|
| **Auto-ingest** (`AUTO_INGEST = TRUE`) | Cloud **event notifications**: S3 via SQS / SNS / EventBridge; GCS via **Pub/Sub** + a notification integration; Azure via **Event Grid** + a notification integration | External stages (internal stages: preview, AWS only) |
| **REST API** | Your app calls the **`insertFiles`** endpoint (key-pair or workload identity auth) | Any external stage, named internal stage or table stage |

```sql
CREATE PIPE orders_pipe AUTO_INGEST = TRUE AS
  COPY INTO orders FROM @orders_stage FILE_FORMAT = (TYPE = JSON);
```

- **Load metadata:** each pipe remembers the files it processed in the **last 14 days** (by path and name) and ignores them, even if modified. Bulk COPY keeps separate table metadata for **64 days**. Don't load the same files with both methods.
- **Backfill:** auto-ingest only sees files that arrive **after** notifications are set up. `ALTER PIPE ... REFRESH` queues files staged in the **last 7 days**.
- **Errors:** default **`ON_ERROR = SKIP_FILE`** (bulk COPY defaults to `ABORT_STATEMENT`). Snowpipe can send **error notifications** through a notification integration.
- **Order** isn't guaranteed: Snowpipe generally loads older files first, but multiple processes pull from the queue.
- Transformations: same simple `SELECT` options as bulk COPY. No joins, filters or aggregations; transform afterwards with dynamic tables or streams and tasks.
- **Billing:** a **fixed number of credits per GB loaded**, with no warehouse and **no per-file charge**. Text files (CSV, JSON, XML) are billed on **uncompressed** size; binary files (Avro, ORC, Parquet) on their stored size. (This replaced the older per-second compute plus per-1,000-files model in 2025.)
- Monitor with `SYSTEM$PIPE_STATUS`, `COPY_HISTORY` and `PIPE_USAGE_HISTORY`.

## Snowpipe Streaming (rows, not files)

- Writes **rows directly into tables** with no staged files. Clients: **Java, Python and Node.js SDKs**, a **REST API**, and the **Snowflake Connector for Kafka**.
- **Latency as low as ~5 seconds**; up to **20 GB/s per table** (high-performance architecture). Serverless, billed per **uncompressed GB** ingested.
- Data flows through **channels** into a **PIPE** object (which can apply COPY-style transformations). **Named channels** use **offset tokens** for ordered, **exactly-once** delivery (good for Kafka partitions and CDC). **Elastic channels** are managed by Snowflake (at-least-once, no order guarantee).
- Targets: standard tables and Snowflake-managed Iceberg tables.

> **Exam tip:** Data already lands as **files** → **Snowpipe**. Data arrives as **rows/events** and needs seconds of latency → **Snowpipe Streaming**. Large scheduled batch with a warehouse → **bulk COPY**.

## Streams (change data capture)

- A **stream** records **DML changes** (inserts, updates, deletes, including `COPY INTO`) to a source object since its **offset**. It stores **no data**, only the offset; it reads changes from the table's version history using hidden change-tracking columns.
- Sources: standard tables (including shared tables), views (including secure views), **directory tables**, dynamic tables, Iceberg tables, event tables, external tables.
- Extra columns: **`METADATA$ACTION`** (INSERT / DELETE), **`METADATA$ISUPDATE`** (an update appears as a DELETE + INSERT pair with TRUE), **`METADATA$ROW_ID`**.

| Type | Tracks | Sources |
|---|---|---|
| **Standard** (delta) | Inserts, updates, deletes (net change) | Tables, dynamic tables, views, directory tables, managed Iceberg |
| **Append-only** (`APPEND_ONLY = TRUE`) | **Inserts only**; faster for ELT | Tables, dynamic tables, views, managed Iceberg |
| **Insert-only** (`INSERT_ONLY = TRUE`) | Inserts only | **External tables**, externally managed Iceberg |

- **Querying a stream doesn't advance it.** The offset moves only when the stream is **consumed in a DML statement** (such as `INSERT INTO ... SELECT FROM stream`) that commits. Multiple streams on one table each have their own offset.
- **Staleness:** a stream goes stale when its offset falls outside the table's data retention. If retention is under 14 days, Snowflake **extends it up to `MAX_DATA_EXTENSION_TIME_IN_DAYS` (default 14)** for unconsumed streams. Check `STALE_AFTER` in `SHOW STREAMS`.

## Tasks

- A **task** runs one SQL statement, a procedure call or procedural logic on a **schedule** (`SCHEDULE = '5 MINUTES'` or `'USING CRON ...'`) or when **triggered**.
- **Compute:** **serverless** (omit `WAREHOUSE`; Snowflake sizes compute, up to the equivalent of **XXLARGE**) or **user-managed** (`WAREHOUSE = ...`). Serverless suits short, stable runs and strict schedules; a warehouse suits fully used warehouses running many tasks.
- **Tasks are created suspended.** `ALTER TASK ... RESUME` starts the schedule; `EXECUTE TASK` runs it once.
- The task owner needs the account-level **`EXECUTE TASK`** privilege. Tasks run as a system user with the **owner role's** privileges.
- **`WHEN SYSTEM$STREAM_HAS_DATA('s')`** skips a run when the stream is empty, so the warehouse isn't used (checking the condition costs a little cloud services time). **Triggered tasks** (a `WHEN` with no schedule) run when the stream has data: at most every **30 seconds** by default (can be lowered to 10). Serverless triggered tasks need `TARGET_COMPLETION_INTERVAL`.
- **Task graphs (DAGs):** one **root task** (holds the schedule) plus child tasks created with **`AFTER`**. Up to **1,000 tasks**, each with up to **100 parents and 100 children**. One optional **finalizer** task runs when the graph finishes, even after failures. Resume children before the root (or use `SYSTEM$TASK_DEPENDENTS_ENABLE`); suspend the **root** to modify the graph.
- `SUSPEND_TASK_AFTER_NUM_FAILURES` auto-suspends after consecutive failures. `USER_TASK_TIMEOUT_MS` defaults to **1 hour**.
- History: `TASK_HISTORY` (Information Schema / Account Usage) and **Snowsight → Monitoring → Task History**.

```sql
CREATE TASK load_orders WAREHOUSE = etl_wh SCHEDULE = '5 MINUTES'
  WHEN SYSTEM$STREAM_HAS_DATA('orders_stream')
AS INSERT INTO orders_clean SELECT * FROM orders_stream WHERE METADATA$ACTION = 'INSERT';
ALTER TASK load_orders RESUME;
```

## Dynamic tables

- A **declarative** pipeline: you write a `SELECT` and a **`TARGET_LAG`**; Snowflake refreshes the table automatically and works out the dependency order between dynamic tables.
- **Minimum target lag is 60 seconds.** `TARGET_LAG = DOWNSTREAM` refreshes only when a downstream dynamic table needs fresh data.
- **`REFRESH_MODE`**: `INCREMENTAL` (only changed rows), `FULL`, `AUTO` (chosen at creation), plus `ADAPTIVE` (incremental that re-initializes after large upstream changes).
- Refreshes run on the **warehouse you specify** (`WAREHOUSE = ...`). Cost = warehouse compute + cloud services + storage.
- Their content comes from the query. They support joins, aggregations and window functions, but not stored procedures or external functions.

| Use | When |
|---|---|
| **Dynamic tables** | The transformation is a SQL `SELECT`; you want Snowflake to schedule refreshes; 1 minute+ freshness is fine |
| **Streams + tasks** | You need procedural logic, procedures, external calls, or precise control over when and how changes apply |
| **Materialized views** | Speed up a single-table query (no joins), always current |

## Openflow

- A managed **data integration service built on Apache NiFi**, with hundreds of processors for structured and unstructured data, batch and streaming.
- Deployment types: **Snowflake deployment** (runs on **Snowpark Container Services**) or **BYOC** (in your own cloud VPC).
- The study guide says Openflow **won't be tested until it's generally available globally**. Know what it is, not the details.
