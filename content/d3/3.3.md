## Drivers

Drivers let **your applications** connect to Snowflake and run SQL. All support **TLS** for traffic to Snowflake.

| Driver | Use |
|---|---|
| **JDBC** | Java apps and most JDBC-based client tools |
| **ODBC** | ODBC-based client apps (for example, BI tools on Windows) |
| **Snowflake Connector for Python** | Python apps (PEP 249 DB-API); the base for many Python tools |
| **Go**, **.NET**, **Node.js**, **PHP PDO** | Apps in those languages |

- The **SQL API** is a **REST API** for submitting SQL statements and checking their status without a driver.
- **Snowpark** (Python, Java, Scala) is a DataFrame library whose code is **pushed down** to run inside Snowflake (see 1.6). It isn't a driver.
- **Snowflake CLI** (`snow`) is the command-line tool for running SQL and managing Snowflake objects and apps. SnowSQL is the older CLI client.

## Connectors

| Connector | What it does |
|---|---|
| **Kafka connector** | Runs in a **Kafka Connect** cluster, reads **topics** and writes rows to tables (usually **one topic → one table**). Loads with **Snowpipe** or **Snowpipe Streaming**. Load only (Kafka → Snowflake). Confluent and open-source Apache Kafka versions; v4 is recommended for new work. |
| **Spark connector** | **Two-way**: read Snowflake tables into Spark DataFrames and write DataFrames back. Uses the JDBC driver and pushes queries down to Snowflake. Snowflake suggests **Snowpark** as an alternative that keeps all processing in Snowflake. |
| **Python connector** | See drivers. Includes pandas support (`write_pandas`, `fetch_pandas_all`). |
| **Native connectors** | Snowflake-built connectors that ingest from SaaS apps and databases, for example **ServiceNow, Google Analytics, MySQL, PostgreSQL, SharePoint**. Many run as Native Apps or on Openflow. |

Partner tools (ETL, BI, ML) connect through these drivers and connectors. **Partner Connect** in Snowsight sets up trial accounts with many partners.

## Integrations

An **integration** is an **account-level object** (not in a schema) that connects Snowflake to an outside service. By default **only ACCOUNTADMIN** can create integrations (the global **`CREATE INTEGRATION`** privilege can be granted to other roles).

| Type | Purpose |
|---|---|
| **Storage** | Access **external cloud storage** (stages) without passing credentials |
| **API** | Reach an **HTTPS API**: cloud API gateways for **external functions**, **Git** repositories, external MCP servers |
| **Notification** | Cloud queues and messaging: Snowpipe auto-ingest (GCS / Azure), error notifications, email, webhooks |
| **Security** | SSO / SAML, OAuth, SCIM (see 2.1) |
| **External access** | Let UDF and procedure code call external network locations (with **network rules** and **secrets**) |
| **Catalog** | Connect to external Iceberg catalogs |

### Storage integration

- Stores a **Snowflake-generated IAM identity** for your cloud storage (for example, an AWS IAM user) plus **`STORAGE_ALLOWED_LOCATIONS`** (and optional `STORAGE_BLOCKED_LOCATIONS`).
- Your cloud admin grants that identity access to the buckets. Stage creators then use `STORAGE_INTEGRATION = my_int` and **never handle keys or secrets**. This is the **recommended** way to connect external stages.
- **One integration can serve many external stages**. The stage URL must fall inside the allowed locations.
- AWS setup: create an IAM role and policy → `CREATE STORAGE INTEGRATION ... STORAGE_AWS_ROLE_ARN = '...'` → `DESC INTEGRATION` to get **`STORAGE_AWS_IAM_USER_ARN`** and **`STORAGE_AWS_EXTERNAL_ID`** → add them to the role's **trust policy**.
- Creating the stage needs `CREATE STAGE` on the schema plus **`USAGE` on the integration**. People who only **load or unload** through the stage need `USAGE` on the **stage**, not on the integration.

```sql
CREATE STORAGE INTEGRATION s3_int TYPE = EXTERNAL_STAGE STORAGE_PROVIDER = 'S3' ENABLED = TRUE
  STORAGE_AWS_ROLE_ARN = 'arn:aws:iam::123456789012:role/snowflake_access'
  STORAGE_ALLOWED_LOCATIONS = ('s3://my-bucket/raw/');
CREATE STAGE raw_stage URL = 's3://my-bucket/raw/' STORAGE_INTEGRATION = s3_int;
```

### API integration

- Stores details of an **HTTPS API**: `API_PROVIDER`, **`API_ALLOWED_PREFIXES`** (and blocked prefixes), and the credentials or identity to use.
- **External functions:** call code behind a cloud API gateway (`aws_api_gateway`, `azure_api_management`, `google_api_gateway`) from SQL.
- **Git:** `API_PROVIDER = git_https_api`.

### Git integration

- Connects a **remote Git repository** (GitHub, GitLab, Bitbucket, Azure DevOps, AWS CodeCommit, or any HTTPS Git URL) to a **Git repository clone** in Snowflake, a **schema-level object**.
- Steps: (optional) a **secret** with a username and personal access token, or OAuth → an **API integration** with `git_https_api` → **`CREATE GIT REPOSITORY ... ORIGIN = 'https://...' API_INTEGRATION = ...`**.
- **`ALTER GIT REPOSITORY r FETCH`** pulls the latest branches, tags and commits. Files are addressed like a stage: `@r/branches/main/path/file.sql`.
- Use files from the repo: **`EXECUTE IMMEDIATE FROM @r/branches/main/setup.sql`**, procedure and UDF handlers, Streamlit apps, notebooks.
- From most Snowflake code the repo is **read-only**. Only **Workspaces, Streamlit apps and notebooks** can commit and push changes.

```sql
CREATE API INTEGRATION git_int API_PROVIDER = git_https_api
  API_ALLOWED_PREFIXES = ('https://github.com/my-org') ALLOWED_AUTHENTICATION_SECRETS = (git_secret) ENABLED = TRUE;
CREATE GIT REPOSITORY my_repo ORIGIN = 'https://github.com/my-org/pipelines.git'
  API_INTEGRATION = git_int GIT_CREDENTIALS = git_secret;
```

> **Exam tip:** "Load from S3 without storing keys in the stage" → **storage integration**. "Call an external REST service from SQL" → **API integration** + external function (or an external access integration for UDF code). "Run SQL scripts kept in GitHub" → **API integration + Git repository + `EXECUTE IMMEDIATE FROM`**.
