## Warehouse types

| Type | Use it for |
|---|---|
| **Standard – Gen 1** | General SQL workloads (the original hardware). |
| **Standard – Gen 2** | Newer hardware and software: faster for most analytics and especially DML (`MERGE`, `UPDATE`, `DELETE`). Higher credit rate per hour, but usually finishes sooner. |
| **Snowpark-optimized** | **Much more memory per node** (about 16× standard), for memory-intensive work: ML training, large UDFs/UDTFs, Snowpark Python processing. |

Notebooks use a default warehouse for their runtime (noted in the guide as not tested until GA).

## Sizes & credits

| XS | S | M | L | XL | 2XL | 3XL | 4XL | 5XL | 6XL |
|---|---|---|---|---|---|---|---|---|---|
| 1 | 2 | 4 | 8 | 16 | 32 | 64 | 128 | 256 | 512 |

Credits per hour for a Gen 1 Standard warehouse. **Each size up doubles compute and credit rate.**

- Billed **per second**, with a **60-second minimum** every time the warehouse starts or resumes.
- Resizing a running warehouse affects **new and queued** queries; running queries finish on the old size.
- Credit usage calculation: `credits/hr × hours running × clusters`. Example: an M (4 credits/hr) running 30 min = 2 credits.

## Scale **up** vs scale **out**

| Problem | Fix |
|---|---|
| Complex, slow queries; **spilling** to disk | **Scale up** (bigger size) |
| Many concurrent users; **queuing** | **Scale out** (multi-cluster warehouse — Enterprise) |

Scaling up does **not** fix concurrency; scaling out does **not** speed up a single query.

## Multi-cluster warehouses (Enterprise+)

- `MIN_CLUSTER_COUNT` / `MAX_CLUSTER_COUNT`.
- **Maximized mode:** min = max, all clusters always run when the warehouse runs.
- **Auto-scale mode:** min < max, clusters start and stop with load, governed by the **scaling policy**:

| Policy | Starts a cluster | Shuts a cluster down | Favors |
|---|---|---|---|
| **Standard** (default) | Immediately when a query queues (or the system detects more queries than clusters can handle) | After 2–3 consecutive checks of low load | **Performance** / minimal queuing |
| **Economy** | Only if the system estimates enough load to keep it busy **≥ 6 minutes** | After 5–6 consecutive checks | **Cost** / fully loading running clusters |

> **Exam tip:** "Some queuing is acceptable, minimize cost" → **Economy**. "Users must never wait" → **Standard**.

## Auto-suspend / auto-resume

- `AUTO_SUSPEND` = seconds of inactivity before suspending (default 600 when created via SQL). `AUTO_RESUME = TRUE` restarts on the next query.
- A suspended warehouse uses **no credits**, but loses its **local disk (warehouse) cache**.
- Short auto-suspend for bursty/ad-hoc work; longer for BI dashboards that benefit from a warm cache. Avoid values below 60 s — the 60-second minimum means frequent resume cycles can cost more.

## Choosing configs by workload

| Workload | Typical setup |
|---|---|
| **Ad-hoc queries** | Small–medium, short auto-suspend, auto-resume on |
| **Data loading** | Size by number of files (more files load in parallel); bigger isn't always better for a few files; separate from BI |
| **BI & reporting** | Multi-cluster auto-scale for concurrency; longer auto-suspend for cache |
| **Different teams** | **Separate warehouses** per team/workload — isolation and cost attribution |
| **Complex queries** | Larger size |
