## Micro-partitions

- All table data is automatically divided into **micro-partitions**: contiguous units of **50–500 MB of uncompressed data** (smaller once compressed), stored **columnar** and **compressed**.
- They are **immutable** — DML writes new micro-partitions; old ones are kept for Time Travel / Fail-safe.
- For each micro-partition, metadata records the **range of values (min/max)** for each column, the number of distinct values, and other stats.
- The optimizer uses this metadata for **pruning**: skipping micro-partitions that can't match the filter.
- No user partitioning is needed; partitioning is automatic, in load order.

## Clustering

- **Clustering depth** = average depth of overlapping micro-partitions for given columns. Lower = better clustered = better pruning.
- Check with `SYSTEM$CLUSTERING_INFORMATION('table', '(col)')` and `SYSTEM$CLUSTERING_DEPTH`.
- A **clustering key** tells Snowflake how to co-locate rows; **Automatic Clustering** then reclusters in the background (serverless, billed credits).
- Use clustering keys for **very large (multi-TB) tables** whose queries filter on the same columns and whose pruning is poor. Not worth it for small or frequently churning tables.
- Good keys: columns used in filters/joins with **moderate cardinality** (e.g., date rather than a timestamp or unique ID). Max 3–4 columns recommended.

## Table types

| Type | Persists | Time Travel | Fail-safe | Notes |
|---|---|---|---|---|
| **Permanent** | Until dropped | 0–1 day (Standard), up to **90** (Enterprise) | **7 days** | Default |
| **Transient** | Until dropped | 0–1 day | **None** | Lower storage cost for re-creatable data (staging, ETL) |
| **Temporary** | **Session only** | 0–1 day | **None** | Not visible to other sessions; dropped at session end |
| **External** | Metadata only | No | No | Read-only; data stays in files in an **external stage** |
| **Apache Iceberg™** | Data in **your cloud storage** (external volume) | Yes (Snowflake-managed) | No | Open table format; **Snowflake** or an **external catalog** (e.g., AWS Glue, Snowflake Open Catalog) |
| **Dynamic** | Until dropped | Yes | Yes | Defined by a query + `TARGET_LAG`; Snowflake refreshes it automatically (incremental or full) |

Also: **Hybrid tables** (Unistore, row-store for low-latency single-row operations) and **event tables** (logging/tracing).

- A temporary table can have the same name as a permanent table — within that session the temporary one **hides** the permanent one.
- Transient/temporary are good when you don't need Fail-safe and want to save storage cost.
- Transient databases/schemas make all their tables transient.

## View types

| View | Key facts |
|---|---|
| **Standard** | Stored query; no storage; computed at query time |
| **Materialized** (Enterprise) | Results are **precomputed and stored**; maintained automatically by a background (serverless) service; **single table only** (no joins), limited functions; good for repeated expensive aggregations on slowly-changing data |
| **Secure** | Hides the **view definition** and internals from non-owners; some optimizations are disabled to avoid data leakage, so can be slower; **required for sharing** views via Secure Data Sharing. Can be standard or materialized |
