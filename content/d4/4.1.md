## Query Profile

**Query Profile** (Snowsight → **Monitoring → Query History** → select a query → **Query Profile**) shows the execution plan as a graph of **operator nodes** (TableScan, Filter, Join, Aggregate, Sort…). It also shows:

- **Most Expensive Nodes**: the operators that used the most time.
- **Statistics**: pruning (partitions scanned vs total), spilling (bytes spilled to local / remote storage), network and I/O.
- **Query insights**: Snowflake's own messages about conditions that affect performance (also in the `ACCOUNT_USAGE.QUERY_INSIGHTS` view).

Query History in Snowsight covers the **last 14 days**. The **Grouped Queries** view groups repeated queries that have the same parameterized text.

## The four problems to recognize

| Symptom in Query Profile | What it means | Fixes |
|---|---|---|
| **Bytes spilled to local storage / remote storage** | Not enough warehouse **memory**, so intermediate results spill to local disk, then to **remote** cloud storage (much slower) | **Bigger warehouse** (more memory and local disk), or process data in **smaller batches**. (Snowpark-optimized warehouses for memory-heavy code) |
| **Inefficient pruning**: *Partitions scanned* close to *Partitions total* | The filter can't skip micro-partitions. A Filter operator above TableScan that removes many rows is another sign | Filter on well-clustered columns, add a **clustering key**, or use **search optimization** for point lookups; avoid functions on filter columns |
| **Exploding join**: the Join produces far more rows than its inputs | A missing join condition (**Cartesian product**) or a condition that matches many rows on both sides | Fix the join condition; check for duplicate keys |
| **Queuing** (queued overload time) | The warehouse is busy with other queries | **Scale out** (multi-cluster warehouse, Enterprise) or move queries to **another warehouse**. Bigger size doesn't fix concurrency |

Other insights to know: **No filter on table scan**, **Filter not selective**, **LIKE with a leading wildcard** (consider search optimization), **Join with no join condition**, **Unnecessary UNION** (`UNION` removes duplicates; use `UNION ALL` when you don't need that), **Remote spilling**, **Queued overload**.

> **Exam tip:** Spilling → **scale up**. Queuing → **scale out**. Poor pruning → **clustering / search optimization**, not a bigger warehouse.

## ACCOUNT_USAGE views for performance

| View | Use | Notes |
|---|---|---|
| **`QUERY_HISTORY`** | Every query: user, role, warehouse, elapsed / compilation / execution time, **queued_overload_time**, **queued_provisioning_time**, bytes scanned, **partitions_scanned / partitions_total**, **bytes_spilled_to_local/remote_storage**, **percentage_scanned_from_cache**, `query_parameterized_hash` | 365 days, up to **45 min** latency. `INFORMATION_SCHEMA.QUERY_HISTORY` = last 7 days, real time |
| **`QUERY_ATTRIBUTION_HISTORY`** | **Warehouse credits per query** (`CREDITS_ATTRIBUTED_COMPUTE`, plus QAS credits) | 365 days, up to **8 h** latency. **Excludes warehouse idle time** and very short queries (≤ ~100 ms) |
| **`WAREHOUSE_LOAD_HISTORY`** | Average running vs **queued** load per warehouse | Find queuing |
| **`WAREHOUSE_METERING_HISTORY`** | Credits per warehouse per hour | Total cost, including idle time |
| **`QUERY_ACCELERATION_ELIGIBLE`** | Queries that could benefit from QAS | See 4.2 |

Group repeated queries with `QUERY_PARAMETERIZED_HASH` (same query with different literal values) to find the most expensive **patterns**, not just single runs.

```sql
-- Most expensive query patterns in the last 30 days
SELECT query_parameterized_hash, COUNT(*) AS runs, SUM(credits_attributed_compute) AS credits
FROM snowflake.account_usage.query_attribution_history
WHERE start_time >= DATEADD(day, -30, CURRENT_TIMESTAMP())
GROUP BY 1 ORDER BY credits DESC LIMIT 10;
```

## Workload management best practices

- **Group similar workloads** on the same warehouse. Tuning is simpler when a warehouse runs similar queries; very different queries waste the benefit (a size that suits one wastes credits on another).
- **Separate different workloads** (loading vs BI vs data science, or by team) onto their own warehouses for isolation, sizing and cost attribution.
- Size for the workload: complex queries → larger; many concurrent users → multi-cluster; loading → match the number of files.
- **`MAX_CONCURRENCY_LEVEL`** (default **8**) limits how many queries run at once on a cluster. Lowering it gives each query more resources but can cause more queuing.
- Use **`STATEMENT_TIMEOUT_IN_SECONDS`** and **`STATEMENT_QUEUED_TIMEOUT_IN_SECONDS`** to stop runaway or stuck queries, and resource monitors to cap cost (see 2.3).
