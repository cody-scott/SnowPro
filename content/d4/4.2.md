## Pick the right tool

| Problem | Tool | Edition | Compute |
|---|---|---|---|
| Outlier queries with **large scans** and selective filters/aggregations hog the warehouse | **Query acceleration service** | Enterprise | Serverless, billed per second when used |
| **Point lookups** that return a few rows from a big table; substring / regex / `SEARCH` / semi-structured lookups | **Search optimization service** | Enterprise | Serverless maintenance + storage |
| Range filters and sorts on the same columns over a **multi-TB** table with poor pruning | **Clustering key** (Automatic Clustering) | All | Serverless reclustering |
| The same expensive **aggregation / projection on one table**, run often, on slowly changing data | **Materialized view** | Enterprise | Serverless refresh + storage |

All four cost credits in the background, so turn them on only where queries benefit enough to pay for them.

## Query acceleration service (QAS)

- **Offloads parts of a query** (mainly scanning and filtering) to shared serverless compute, so **outlier queries** don't slow the whole warehouse.
- Eligible patterns: **large scans with an aggregation or selective filter**, and large scans that **insert or copy** many rows.
- Common reasons a query is **not eligible**: too few partitions to scan, filters not selective enough (or GROUP BY cardinality too high), a `LIMIT` that blocks it, or nondeterministic functions such as `RANDOM`.
- Enable per **warehouse**: `ALTER WAREHOUSE wh SET ENABLE_QUERY_ACCELERATION = TRUE`. It's **on by default for Gen2 standard and multi-cluster warehouses**.
- **`QUERY_ACCELERATION_MAX_SCALE_FACTOR`** caps the extra compute as a multiple of the warehouse size: **default 8**; **0 = no limit**. Example: a Medium (4 credits/h) with scale factor 5 can lease up to 20 more credits/h.
- Find candidates with the **`QUERY_ACCELERATION_ELIGIBLE`** view or **`SYSTEM$ESTIMATE_QUERY_ACCELERATION('<query_id>')`**. Credits are shown separately (`CREDITS_USED_QUERY_ACCELERATION`).

## Search optimization service

- Builds a **search access path**: a persistent structure recording which values might be in each micro-partition, so more partitions can be skipped.
- Best for **selective point lookups** (one or a few rows), equality and `IN` filters, **substring and regex** (`LIKE`, `ILIKE`, `RLIKE`), **`SEARCH` / `SEARCH_IP`**, fields in **VARIANT / OBJECT / ARRAY** columns, and some geospatial functions.
- Enable: `ALTER TABLE t ADD SEARCH OPTIMIZATION;` (whole table) or `... ON EQUALITY(col), SUBSTRING(col2)`. Requires **OWNERSHIP** of the table and **`ADD SEARCH OPTIMIZATION`** on the schema. Users just need `SELECT`.
- Building the access path runs in the background (no warehouse) and takes time; queries aren't accelerated until it finishes (`search_optimization_progress` in `SHOW TABLES`). It's kept up to date as DML changes the table.
- A **cast on the column** (`CAST(col AS NUMBER) = 2`) prevents its use; a cast on the constant is fine.

## Clustering keys

- Co-locate similar rows in the same micro-partitions so filters prune better (micro-partitions are covered in 1.5).
- Use them when: the table is **very large (multi-TB)**, queries **filter or sort on the same columns**, and pruning is poor (high clustering depth). Not worth it for small or **constantly changing** tables: frequent changes make reclustering expensive.
- **Choosing columns:** first, columns used in **selective filters** (often a **date**); then **join** columns. Aim for **3–4 columns max**.
- **Cardinality:** not too low (a boolean prunes little) and not too high (a unique ID or timestamp is costly to maintain). For high cardinality, cluster on an **expression** such as `TO_DATE(ts)`. In a multi-column key, order columns from **lowest to highest cardinality**.
- **Automatic Clustering** reclusters in the background on serverless compute (no warehouse to set); it doesn't block DML. Pause with `ALTER TABLE t SUSPEND RECLUSTER` / `RESUME RECLUSTER`.
- Check with `SYSTEM$CLUSTERING_INFORMATION` and `SYSTEM$CLUSTERING_DEPTH`.

```sql
ALTER TABLE events CLUSTER BY (TO_DATE(event_ts), event_type);
```

## Materialized views

- **Precomputed, stored** query results, maintained automatically by a background service. **Always current**: if the stored results lag behind, Snowflake reads the newest data from the base table.
- The optimizer can **rewrite queries against the base table** to use a materialized view automatically.
- **Limits:** a **single table only** (no joins, including self-joins); **no UDFs, window functions, `HAVING`, `ORDER BY` or `LIMIT`**; only some aggregates (such as `SUM`, `COUNT`, `MIN`, `MAX`, `AVG`), which can't be nested.
- Good fit: an expensive aggregation or filter on one large table that's queried often and changes slowly. Frequent changes to the base table mean frequent (costly) maintenance.
- Materialized views can have their own clustering key. Reclustering the base table also triggers materialized view maintenance (more cost).

> **Exam tip:** "A few rows out of billions, by ID or text search" → **search optimization**. "Some huge ad-hoc scans slow everyone else down" → **QAS**. "Date-range filters on a multi-TB table scan most partitions" → **clustering key**. "Same aggregate on one table, over and over" → **materialized view**. For **joins** across tables, use a **dynamic table** instead.
