## Three caches

| Cache | Where | Holds | Needs a running warehouse? | Lifetime |
|---|---|---|---|---|
| **Query result cache** (persisted query results) | Kept by Snowflake, outside any warehouse | **Results** of queries already run | **No**: query execution is skipped | **24 h**, reset each time it's reused, up to **31 days** from the first run |
| **Metadata cache** | Cloud services layer (metadata management) | Micro-partition metadata: row counts, **min/max** per column, distinct values | **No** for metadata-only queries | Always maintained |
| **Warehouse cache** (local disk / data cache) | The warehouse's local disk | **Table data** read by earlier queries | Yes, and it's per warehouse | **Dropped when the warehouse suspends** (or resizes down) |

## Query result cache

A repeated query reuses the stored result (no warehouse, near-instant) only if **all** of these hold:

- The query text **matches exactly**. Even a different **table alias** or **lowercase keywords** prevents full reuse.
- No **non-reusable functions** such as `RANDOM`, `UUID_STRING` or `RANDSTR` (functions that return different results each run), no **external functions**, and no **hybrid tables**.
- The **underlying data hasn't changed**, and the table's micro-partitions haven't changed (for example, by reclustering).
- The role has the **privileges** needed on all the tables (for `SHOW` queries, it must be the same role).
- Settings that affect the result haven't changed, and the result is still stored.

More facts:
- Reuse is **on by default**. Turn it off with **`USE_CACHED_RESULT = FALSE`** (account, user or session), for example when benchmarking.
- The result cache is shared across users: anyone with the right privileges who runs the identical query can reuse it.
- **`RESULT_SCAN(LAST_QUERY_ID())`** (or the `->>` pipe operator) queries a previous result as a table, which is handy after `SHOW`, `DESCRIBE` or `CALL`.

```sql
SHOW TABLES;
SELECT "name", "rows" FROM TABLE(RESULT_SCAN(LAST_QUERY_ID())) WHERE "rows" = 0;
```

## Metadata cache

- Snowflake keeps metadata about every micro-partition (value ranges, distinct counts, row counts) in the cloud services layer.
- Queries such as `SELECT COUNT(*) FROM t` or `MIN`/`MAX` of a column can be answered **from metadata alone**: Query Profile shows a **Metadata-based Result** and **no warehouse** processes it.
- The same metadata drives **pruning** at query time.

## Warehouse cache

- A running warehouse caches the table data it reads on local storage. Later queries on the **same warehouse** that read the same data scan less from remote storage.
- **Larger warehouses have a larger cache.** The cache is **lost on suspend**.
- Track it with **`percentage_scanned_from_cache`** in `QUERY_HISTORY`. The Query Profile shows "Percentage scanned from cache".
- **Trade-off:** a short `AUTO_SUSPEND` saves credits but loses the cache; a longer one keeps the cache warm for **BI / dashboards** with repeated, similar queries. Running similar queries on the same warehouse makes the cache more useful.

> **Exam tip:** "Same query, data unchanged, returns instantly even though the warehouse is suspended" → **result cache**. "`COUNT(*)` with no warehouse running" → **metadata**. "Dashboards got slower after we reduced auto-suspend" → lost **warehouse cache**.
